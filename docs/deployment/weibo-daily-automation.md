# 微博超话每日自动任务

## 启用

更新并重新构建后端、前端；后端启动时按现有 `spring.sql.init.mode=always` 执行 `schema.sql`，自动创建 `daily_activity_plan`、`activity_task`、`activity_templates` 和 `activity_account_pause` 四张新表。若自行关闭了 SQL 初始化，先在应用数据库执行该文件。已有表通过 `CREATE TABLE IF NOT EXISTS` 保留。

在「平台账号」中保存微博登录态、启用账号，在「微博超话」中为该账号配置并启用每个超话，填写有效的 HTTPS 微博超话地址。后台进程和浏览器 worker 持续运行即可，不必保持网页打开。容器登录与存储配置参见 [Docker 部署](weibo-docker.md)。

## 每日额度和时间

以 `Asia/Shanghai` 日期为准，执行窗口为 08:00（含）至 22:00（不含）。每个账号的每个启用超话每天分别生成：

| 操作 | 当天目标 |
| --- | --- |
| 签到 | 1 次 |
| 发帖 | 1 个 |
| 转发 | 随机 2–4 个不同帖子 |
| 评论 | 随机 4–6 个不同帖子 |
| 浏览 | 随机 40–50 个不同帖子 |

目标生成后持久保存，重启或点击「检查/补建今日计划」都不重新抽数量。动作分散在剩余执行窗口，每次调度至多执行一个，按剩余任务量采用 5–60 秒冷却，普通任务量采用一分钟。浏览器加载和实际阅读还会占用时间。大量账号、帖子不足或平台不可用时，页面如实显示未完成数量，不把失败算成达标。22:00 后不再执行当天动作，也不跨天补做。

后端启动 10 秒后开始检查任务，之后每 5 秒检查一次。确有需要时可设置 `weibo.activity.initial-delay-ms`、`weibo.activity.poll-delay-ms`（环境变量 `WEIBO_ACTIVITY_INITIAL_DELAY_MS`、`WEIBO_ACTIVITY_POLL_DELAY_MS`）；这些配置只控制队列检查周期，不改变每日额度和操作窗口。多个应用实例使用同一 MySQL 命名锁串行执行，锁连接必须在整个浏览器动作期间保持可用。连接池至少需要两条连接，一条持锁，其他连接用于计划事务和进度写入。

## 任务页面

「任务控制」展示各超话目标、成功数量、状态、下一项计划和近期记录，15 秒刷新。页面未打开时后端照常执行。

「编辑内容模板」为当前超话分别填写发帖和评论候选文案，一行一个，`{topic}` 自动替换超话名称。保存后更新尚未执行的任务文案，已经执行或结果待核实的动作不重发。

## 暂停和恢复

登录过期或要求验证码时暂停整个账号，暂停标记跨重启、跨天保留。在「平台账号」手动完成登录或验证并保存状态，再到「任务控制」点击该账号的「检查并恢复账号」。后台重新核实登录状态，补建缺失的今日计划并分散安排剩余动作。即使账号今天没有计划，账号恢复区也会显示该账号。

只有明确成功的动作计入完成数。提交前确定失败的动作延后五分钟重试，最多尝试三次；提交后没有可靠确认、连接中断或重启遗留的执行中任务会标为 `UNKNOWN`（待核实），不会自动重发。遗留执行中任务超过十分钟后转为待核实。待核实记录和所选帖子会保留，便于人工检查微博记录。当前页面不提供待核实动作自动重试或额度清零按钮。

## 验证范围

本功能使用隔离测试库、模拟浏览器流程和前端生产构建验证。微博页面控件可能随平台更新变化；更新后的选择器需要在实际账号环境核实。本地测试不向真实微博发送帖子、评论或转发，也不表示服务已经部署到服务器。
